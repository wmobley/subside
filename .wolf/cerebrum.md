## Key Learnings

- **Project:** subside
- **Description:** **Subsidence System for Insight and Data Exploration** — a statewide portal that
- **ui/**: most Displacement runs render via a cheap pre-rendered PNG `ImageOverlay` (STAC asset key `overlay`), not the streamed COG (`StacCogLayer`) — but `itemLayers(item)` (ui/src/lib/stacApi.js) still returns the real `cog` asset alongside the `overlay` one, so per-pixel sampling for an overlay-rendered run is possible by lazily parsing just that COG on demand (see `sampleCogValueAt` in ui/src/lib/pixelSample.js), not by re-rendering it as a layer.
- **ui/**: `georaster` (~580KB) MUST be imported via `import('georaster')` (dynamic), never a static top-level `import ... from 'georaster'` — a static import anywhere in the module graph pulls the whole bundle out of its lazy chunk into the main bundle. `npm run build`'s chunk-size output is the way to catch this; StacCogLayer.jsx's existing `loadGeoraster` already does this correctly — match that pattern in any new module that needs georaster.
- **ui/styles.css**: the generic `.slp-row .slp-name` rule (`.slp-name` truncated to one line inside any `.slp-row`) has specificity (0,2,0). A new single-class rule like `.slp-run-name { white-space: normal }` will NOT override it regardless of source order. To override truncation for a specific row variant, match the ancestor-combinator shape, e.g. `.slp-run-row .slp-name` (also 0,2,0, so it wins by being later in the file).
- **ui/ — critical**: `georaster-layer-for-leaflet@4.1.2` (verified against BOTH dist entry points package.json actually resolves — `main` and `module` — not just one bundle) has NO click/interactive-target support whatsoever: it's a plain `L.GridLayer.extend({...})` that never calls `addInteractiveTarget` and never fires `'click'`/`'contextmenu'` on the layer. `layer.on('click', ...)` on a `GeoRasterLayer` instance (as StacCogLayer.jsx used to do) is a silent no-op — it never throws, it just never fires. Real interactivity for a StacCogLayer-rendered pixel MUST be done at the map level (`useMapEvents({click, contextmenu})` in the parent), checking the click's lat/lon against each layer's own `getBounds()` + a point-sampler (see `findSampledRunAt` in StacResults.jsx). Don't add `layer.on(...)` calls to StacCogLayer expecting them to fire.
- **ui/**: `GeoRasterLayer`'s `resampleMethod` option only controls the FIRST of two internal resample stages (georaster-stack reading/reprojecting into `tileRasters`, per georaster-layer-for-leaflet.js's own comment "this is separate from the resampleMethod that does the actual reprojection"). The final canvas-draw step that calls `pixelValuesToColorFn` is hardcoded to `method: "near"` internally — but since that stage just copies whatever the first stage already computed, setting `resampleMethod: 'bilinear'` (added to StacCogLayer.jsx) still visibly smooths tiles; it isn't overridden back to nearest.
- **ui/ — data**: SUBSIDE's displacement/velocity COGs use literal IEEE `NaN` as their nodata sentinel (confirmed via `gdalinfo`'s `noDataValue` field on a real local COG — not a numeric fill like -9999). This is why `bilinear` resampling is safe here: NaN excluded from geowarp's interpolation weighting (verified with a standalone geowarp test) rather than producing garbage blended colors at data-gap edges. If a future raster uses a numeric nodata sentinel instead, re-verify this before assuming bilinear is still safe.
- **tapis/register_pods.py — critical**: CORS for the API pod has TWO independent layers that both must allow the UI's origin: (1) FastAPI's `CORSMiddleware` via `SUBSIDE_CORS_ORIGINS` env var, and (2) Tapis Pods' own ingress-level `cors_allow_origins` pod-spec field (visible via `GET`ing the pod — a browser CORS error can come from either, and layer 2 blocks before the request ever reaches the FastAPI app so app-level logs won't show it). `register_pods.py`'s `build_specs()` now sets both, deployment-derived from `ui_url`. Before assuming an app-level CORS fix is sufficient, check the live pod's actual `cors_allow_origins` (the platform layer) too.
- **ui/ — bug pattern**: `combinedRange()` in StacResults.jsx (the min/max across ALL currently-shown runs of a kind) was computed and shown in the panel's `RasterLegend`, but each individual `StacCogLayer` was colored using its OWN per-run `range` instead — meaning the legend didn't match what was actually rendered, and side-by-side runs weren't color-comparable. Watch for this pattern generally: a "combined/summary" value computed for display (a legend, a header stat) silently NOT being the same value actually driving the thing it's summarizing.
- **ui/**: raster color ramps live in `ui/src/lib/colorRamps.js` (VIRIDIS, PLASMA, `rampColor(palette, t)`, `cssGradient(paletteName)`) — the single source of truth for BOTH what StacCogLayer paints on the map AND the legend bars in StacResults.jsx/SubsideAnalysis.jsx (set via inline `style={{background: cssGradient(...)}}`, not a hardcoded CSS gradient). Displacement uses viridis (StacCogLayer's default), velocity uses plasma (`palette="plasma"` passed explicitly, per user request 2026-07-27) — SubsideAnalysis.jsx picks the palette via its own `isVelocityLayer()` helper (same `key==='velocity'||/velocit/i.test(label)` check used elsewhere in that file). Adding a new palette or a new place that needs to show these colors: add the array to colorRamps.js, don't hand-write another hex-stop list or CSS gradient — that's exactly the duplication that caused bug-004-era drift.
- **tapis/register_pods.py — critical**: `t.pods.update_pod(**spec)` does NOT deep-merge the `cors_allow_*` fields — passing only `cors_allow_origins` wiped `cors_allow_methods`/`cors_allow_headers` to `[]` on the live pod (confirmed by the user's paste of the resulting broken state). `cors_max_age` was untouched, so it's tracked independently of the other four. Always set `cors_allow_origins`/`cors_allow_methods`/`cors_allow_headers`/`cors_allow_credentials` together in the same update — never just the one field you're trying to change. This likely generalizes to other multi-field Tapis Pods spec blocks too; don't assume partial-field updates are safe there.
- **ui/ — perf, HTTP/1.1**: `ckan.tacc.utexas.edu` serves over HTTP/1.1 (confirmed via a HAR's `httpVersion` field), so browsers cap concurrent connections to it at ~6. Rendering N `StacCogLayer`s at once each independently calls `parseGeoraster(href)` (a `geotiff.fromUrl` header read) with zero coordination — at N~24-32 this floods the 6-connection budget and tiles get starved/abandoned (no HTTP errors, just never-arriving responses that Leaflet gives up waiting on), which looks like "missing blocks," not a COG-format problem. Fixed with `ui/src/lib/loadQueue.js` (`withLoadSlot`, `MAX_CONCURRENT_LOADS=4`) — every StacCogLayer's open phase now queues through this shared gate. If adding another COG-loading code path in the future, route it through the same queue rather than calling `parseGeoraster`/`loadGeoraster` directly.
- **ui/ — critical, unresolved (bug-008)**: `georaster-stack` (georaster-layer-for-leaflet's tile-read dependency) spawns a POOL OF 3 WEB WORKERS PER LAYER (`this.tileWorkers = range(3).map(() => create_worker())` in node_modules/georaster-stack/core/index.js) and reads actual tile data from inside them. A Worker has its own isolated global scope, so patching `window.fetch` on the main thread — even correctly detecting Range headers, confirmed via debug logging — has ZERO effect on requests issued from inside these workers (verified: a Playwright test showed no change in peak concurrency, actually worse, after installing a global fetch patch). Any future attempt to gate/throttle/observe COG network traffic MUST account for this — main-thread interception (fetch patching, XHR patching, etc.) cannot reach it. A Service Worker could (it intercepts same-origin fetches from Workers too) but is a much bigger architectural change, not yet attempted. The zoom/pan-triggered per-tile request burst across many already-mounted layers (measured peak concurrency 37 in a 20-layer test, vs 11 during the already-throttled initial load) remains a real, unmitigated risk.
- **Testing gotcha**: when load-testing with multiple StacCogLayer instances against the SAME COG url for convenience (no need for N distinct files to exercise per-origin connection-limit behavior), do NOT differentiate instances with a query string like `?instance=N` — georaster's `.ovr`-overview-existence probe does naive string concatenation (`this._url + '.ovr'`), so `foo.tif?instance=5` becomes the nonsensical `foo.tif?instance=5.ovr`, which a static file server will resolve to the original file and return 200 for, making georaster wrongly believe a (garbage) overview exists and fail to parse it. Same URL for all test instances is fine and doesn't affect the connection-limit test's validity (the browser's per-origin cap doesn't care about path/query, only scheme+host+port).
- **Testing gotcha**: don't reset a `window.__counter` debug variable at the top of a React component's render body if you're trying to accumulate a count across multiple async callback-triggered re-renders — the render body re-runs on every state-triggered re-render, silently resetting the counter back to 0 between increments. Initialize such globals once, outside/above the component function, not inside it.

- [2026-07-27] Added a static `import parseGeoraster from 'georaster'` to a new lib module (pixelSample.js) and only caught the ~580KB main-bundle regression by reading `npm run build`'s chunk-size output afterward. It never fired (see the georaster-layer-for-leaflet Key Learning above); the bug was invisible because displacement mostly rendered via ImageOverlay (which does work) until "Render the Cogs" made StacCogLayer universal. For any Leaflet-layer click/interactivity claim, verify with an actual browser click (Playwright or manual) before considering it done — a passing sampling-logic test is NOT evidence the click event itself fires.

## Decision Log

<!-- Significant technical decisions with rationale. Why X was chosen over Y. -->

- [2026-07-27] Displacement runs now always render via the real COG (StacCogLayer), matching velocity — dropped the "prefer the cheap PNG overlay when available" behavior. I flagged the tradeoff first (overlay is near-zero client cost for up to 24 simultaneous runs; the overlay PNG is also a 2nd–98th-percentile-clipped viridis rendering per analysis/h2i_lab/preview.py, not an invertible encoding of the real value) but the user explicitly chose accuracy/consistency over that render-cost saving ("Render the Cogs"). The PNG overlay is now only a fallback for the rare run with no COG asset published at all — those still can't be pixel-sampled (no COG to read). Removed `sampleCogValueAt`/the lazy-COG-read-for-overlay code path from pixelSample.js as dead code once this landed.
- [2026-07-27] Chose a UX/architectural fix (fewer live COGs mounted at once) over a Service Worker for bug-008 (zoom-triggered tile-request burst that main-thread throttling can't reach — georaster-stack's per-layer Worker pool). Per-run visibility flipped from opt-out (all in-view runs shown by default) to opt-in (only the single most-recent run per kind shown by default); added a date-range preset that narrows the STAC search itself, and a client-side location text filter. This directly caps how many StacCogLayer instances (and their Worker pools) can exist simultaneously, sidestepping the network-layer problem entirely rather than trying to fix it after the fact.
- **ui/ — bug pattern (bug-009)**: this opt-in-visibility feature immediately interacted badly with bug-004's "shared color range" fix — that fix computed the shared min/max from every run the viewport's STAC search returned, not just the runs actually rendered. Once most in-view runs stopped being rendered by default, the color scale kept getting pulled around by candidates that were never even drawn. Fixed by scoping combinedRange() to the visible/rendered subset (isRunVisible-filtered), not the full search-result list. General lesson: when a "shared/summary value across a group" feeds something visual (a legend, a color scale), re-check what "the group" means after ANY change to which members of that group are actually active/rendered — the two can silently drift apart.
